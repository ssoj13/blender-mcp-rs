# Blender 5.0: Core

## Longer Data-Block Names

The data-blocks can now have names up to 255 bytes, increased from previous limit of 63 bytes.

Some points to keep in mind when using longer names in Blender 5.0:

* Compatibility with Blender 4.5:
  * Names will be truncated when opening such 5.0 blend-files in Blender 4.5.
  * Linking data-blocks with longer names is not supported at all in Blender 4.5.
    This also includes opening existing 5.0 blend files linking such data-blocks.
* Potential issues on Windows regarding file names.
  * Windows (NTFS) only supports up to 255 chars in its file names.
    This limit can now more easily be reached with longer data-block names,
    when they are used as part of a generated file name. While this issue already existed before,
    it may become more common and visible now.

(blender/blender#137608, blender/blender!137196, blender/blender@fdaaea632863)

## Packed Data

Packed linked data are a key part of an improved asset workflow in Blender.

Packed IDs remain considered as linked data (i.e. they cannot be edited), but they are stored in the current blendfile. This means that they:

* Are not lost in case the library data becomes unavailable.
* Are not changed in case the library data is updated.

These packed IDs are de-duplicated across blend-files, so e.g. if a shot file and several of its dependencies all use the same util geometry node, there will be a single copy of that geometry node in the shot file.

In case there are several versions of a same ID (e.g. linked at different moments from a same library, which has been modified in-between), there will be several packed IDs.

Name collisions are averted by storing these packed IDs into a new type of 'archive' libraries (and their namespaces). These libraries:

* Only contain packed IDs.
* Are owned and managed by their 'real' library data-block, called an 'archive parent'.

Compatibility wise, 5.0+ blendfiles containing packed data will open in Blender 4.5LTS, packed data will be converted to plain regular local data then (as if they had been appended).

For more in-depth info:

* Commit in `main`: blender/blender@4e4976804e
* Pull request: blender/blender!133801
* Technical design: blender/blender#132167
* UI/UX design: blender/blender#140870

## Large Buffers in Blend-Files

The .blend file format has been changed to support larger buffers (blender/blender@59a759b98d1).
This is necessary to be able to store e.g. meshes with more than a few hundred million vertices.
Note that there may still be other aspects of Blender that make it difficult with such large
data-blocks.

This change affects the structure of the file header
as well as the header of each block in the file.
So any code that is parsing .blend files has to be updated.
Checkout the following files for details:
[file header](https://projects.blender.org/blender/blender/src/branch/main/source/blender/blenloader_core/BLO_core_blend_header.hh) and
[block header](https://projects.blender.org/blender/blender/src/branch/main/source/blender/blenloader_core/BLO_core_bhead.hh). 

Blender 4.5 LTS is able to load files stored in this new format, but older Blender versions are not.

## Logging

Most of Blender now uses the same logging system,
including operators reports and background render progress.
The output format has changed, and log levels are easier to control.
(blender/blender#139451)

* `--log-level info` enables all info level log messages, with a moderate amount of output.
  This may be useful to enable in production for troubleshooting issues.
  `--log-level debug` provides additional output aimed at developers, while `--log-level trace`
  is even more verbose.
* `--log-show-memory` shows memory usage on every line.
* `--log-show-source` shows the source code location.
* `--log-list-categories` shows the full list of available categories.

## Big Endian Support Removed

The support for building Blender on big endian systems,
and opening blend-files created from such a build,
[has been removed](https://projects.blender.org/blender/blender/commit/bc80ef136e8af0a355d234205ed6c7b0acaa84ab).
See the [related announcement](https://devtalk.blender.org/t/big-endian-support-deprecation-removal/39098/2)
for details.

## More Path Template Variables

The following new path template variables have been introduced
(blender/blender@56d8c11304,
[documentation](https://docs.blender.org/manual/en/5.0/files/file_paths.html#available-variables)):

- `scene_name`
- `camera_name`
- `node_name`
- `blend_name_lib`
- `blend_dir`
- `blend_dir_lib`

## Command Line Argument for GPU VSync

Added `--gpu-vsync` command line argument,
in most cases this shouldn't need to be set however setting `--gpu-vsync off`
can be used to measure performance where the frame-rate exceeds the displays refresh rate.

(blender/blender@aafef977fb5062759c6ac710f15d41f27511c2c5,
blender/blender@5540b9440a33c42461978c43cf396f56c1e0291a)

## Nodes in NodeGroups now have UI for their Custom Properties

As a follow-up to splitting 'system-defined' IDProperty storage from 'user-defined' ones (aka 'Custom Properties'),
UI to access custom properties of Nodes has been added to the Node tab of the Properties of the Node Editor ([commit](https://projects.blender.org/blender/blender/commit/329112c4d3)):

![New Nodes Custom Properties Panel](images/nodes_customprops_ui.png)

See also the [BPY release notes](./python_api.md#removal-of-unsupported-access-to-runtime-defined-properties-storage-data)
for more details about the IDProperty storage changes.

## Other

- Removed use of the undocumented `TMP` environment variable on UNIX, use `TMPDIR` instead.
  (blender/blender@b07a1adf044108d28d216a59507164484d3523ad)
- Blendfile Compression on saving is now enabled by default (blender/blender!146172, blender/blender@00dbb53131).
  Users who still want to write uncompressed blendfiles by default will have to edit and save again their user preferences.
